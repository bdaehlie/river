# River v0.8.0

This release completes the "Full Path Control Features" milestone. It is about
what River does to a request between accepting it and forwarding it, and what
it refuses to forward at all.

## Breaking changes

Read this section before upgrading.

### Requests are normalized, and malformed ones are rejected

River now canonicalizes every request before anything else looks at it, and
turns away requests that cannot be canonicalized. **This rejects traffic that
v0.7 accepted**, which is the point of the feature, but it may include traffic
you rely on.

Rejected by default:

* An encoded path separator (`%2F`, `%5C`)
* A path that climbs above the root with `..`
* A control character or NUL in the path, literal or encoded
* A malformed percent-encoding
* More than one `Host` header, a `Host` that disagrees with an HTTP/2
  `:authority`, or no `Host` at all

Rewritten rather than rejected: `.` and `..` segments are resolved, runs of `/`
are collapsed, unreserved characters are decoded, and remaining escapes are put
in upper case. The query string is not touched.

Each check can be disabled on its own. If you have an application that genuinely
serves paths containing an encoded slash, for instance:

```kdl
normalization {
    encoded-separators false
}
```

To restore the previous behaviour entirely:

```kdl
normalization {
    default false
}
```

Rejections are logged at `debug` level with the reason, so a request that
suddenly stops working will say which check turned it away. See
[Request Normalization](https://onevariable.com/river-user-manual/config/normalization.html).

### `block-cidr-range` now answers 403

It previously answered 401, while the manual documented 400. Neither is right
for a blocked source address: there is no credential the client could present
that would change the answer. The status is now configurable, so the old
behaviour is `status=401`.

### A bad path control filter is now a configuration error

Filters used to be checked when a service was constructed, which meant a bad
regular expression or an unparseable address range panicked at startup and was
invisible to `--validate-configs`. They are now checked while the configuration
file is read, and reported against the line that has them.

This means configurations that were previously *accepted* but silently broken -
a misspelled setting on an `upsert-header`, an unknown `path-control` stage
name - are now rejected. `--validate-configs` will tell you before you deploy.

## New features

### Routing

A service can now send different requests to different sets of upstream
servers, chosen by URI path and method. Each route carries its own
`connectors` block, so it has its own discovery, load balancing, health
checking, and timeouts.

```kdl
routes {
    route "/api" {
        connectors {
            load-balance { selection "RoundRobin" }
            dns "api.internal" port=8080
        }
    }
    route "/" {
        connectors {
            "10.0.0.1:8080"
        }
    }
}
```

Routes are matched exact first, then by longest prefix, then by regular
expression, in an order fixed at startup. A service with a plain `connectors`
block still means what it always did: one route claiming everything.

See [Routing](https://onevariable.com/river-user-manual/config/routing.html).

### Client address resolution behind a proxy

Filtering and rate limiting used to key on the address of the TCP connection.
Behind a load balancer that is the balancer's address, so deny lists matched
nothing and every client in the world shared one rate limiting bucket.

```kdl
client-ip {
    trusted-proxies "10.0.0.0/8"
}
```

The forwarding header is believed only from a peer inside `trusted-proxies`,
and is read right to left so a client cannot forge its own address.

### Three more lifecycle stages

`response-filters` runs at the last point before a response goes downstream,
including responses served from cache. `request-body` and `response-body` bound
how large a body River will move; they count and reject rather than rewrite.

### More filters

* `allow-cidr-range`, the complement of `block-cidr-range`
* `remove-header-key-glob`, alongside the existing regular expression form
* `remove-header` for an exact name
* `append-header`, which adds without replacing - `Vary` and `Set-Cookie` are
  lists, and replacing them discards what an upstream server said
* Every filter that rejects a request takes `status` and `body`

### Overload controls

```kdl
overload {
    max-concurrent-requests 1000
    read-timeout-ms 30000
    min-send-rate-bytes 1024
}
```

`max-concurrent-requests` sheds once a service has that many requests in
flight - a different question from rate limiting, which bounds one client
rather than the whole service. The timeouts bound how long a slow client can
hold a connection open.

Nothing here is set by default: what a service can take depends on the upstream
servers behind it.

## Testing

This release adds River's first end-to-end integration suite, which runs a real
River process against a real socket. It exists because normalization and request
framing are about what arrives on the wire, and several of these tests send
requests that no HTTP client would agree to construct.

## Known constraints

* **The PROXY protocol and Cloudflare Spectrum are not supported.** Pingora
  0.8.1 has no support to build on. `X-Forwarded-For` is the part of that
  requirement this release covers.
* **Body stages count and reject; they do not rewrite.** Rewriting a body means
  buffering it, which is the denial of service vector these limits exist to
  prevent.
* **An exceeded `response-body` limit may or may not change the status**,
  depending on whether the response header had already been flushed. The
  guarantee is that the oversize body does not arrive in full.
* **Route matching is prefix-based**, with a regular expression form available.
  Evaluating expressions against every request is a performance cliff.
